\begin{frame}{Entrar en ROS va atado a un SO y a una distro}
\centering
\begin{tabular}{ll}
\toprule
\textbf{Tienes} & \textbf{Tu camino} \\
\midrule
Ubuntu 24.04 & \lstinline|apt install|, el camino feliz \\
Ubuntu 22.04 & Solo Humble. ¿Quieres Jazzy? Reinstala el SO \\
Arch u otra Linux & Compilar desde fuente, o un contenedor \\
macOS & Sin camino oficial. VM o Docker \\
Windows & Soporte limitado, WSL2 o Docker \\
\bottomrule
\end{tabular}
\vfill
\begin{block}{Y además}
\lstinline|apt install ros-jazzy-desktop| hoy y dentro de 6 meses instala builds distintos: no hay lockfile. \texttt{rosdep} llama a \texttt{apt}, \texttt{pip}\ldots\ sin fijar versiones. Y el modelo underlay/overlay (\lstinline|source ... setup.bash|) es manual y frágil.
\end{block}
\end{frame}

\begin{frame}{``Usa Docker'' es la respuesta aceptada}
\begin{itemize}
    \item La instalación se vuelve posible, y el equipo comparte una imagen.
    \item Pero tu flujo de trabajo vive dentro de una caja: editor, depurador, USB, red, GPU, GUIs\ldots\ todo cuesta más.
    \item Docker aísla, pero \textbf{no fija el contenido}: un \lstinline|apt-get install| dentro del Dockerfile no es reproducible si no congelas todo a mano.
    \item Se monta una vez, reconstruir es lento, y nadie lo vuelve a tocar.
\end{itemize}
\vfill
\begin{alertblock}{Mensaje clave}
Docker sigue siendo válido para desplegar, pero no debería ser la \textbf{única} fuente de verdad de las dependencias del proyecto.
\end{alertblock}
\end{frame}

\separador{¿Cómo llegamos ahí?}{Todas las máquinas · Sin distro · Declarativo · Reproducible · Rápido · Simple}

\begin{frame}{Cómo llegar (1/2)}
\begin{block}{Todas las máquinas}
Linux, macOS, Windows; x86 y arm64. Tu portátil, la CI y el robot pueden ser máquinas distintas.
\end{block}
\begin{block}{Sin distro}
Una distro de ROS es un proceso de release, no un sistema operativo. Jazzy en Ubuntu 22.04, Kilted en macOS, Humble en Windows\ldots\ y dos a la vez.
\end{block}
\begin{block}{Declarativo}
Tu entorno es un fichero en git: \lstinline|pixi.toml| dice lo que quieres. Vuelves a un estado bueno como vuelves atrás en el código.
\end{block}
\end{frame}

\begin{frame}{Cómo llegar (2/2)}
\begin{block}{Reproducible}
Un lockfile (\lstinline|pixi.lock|) en lugar de una imagen: cada paquete, versión y hash. El mismo entorno en el portátil, en la CI y en el robot.
\end{block}
\begin{block}{Rápido}
Minutos hasta tener el proyecto funcionando. Que lo único lento sea la conexión.
\end{block}
\begin{block}{Simple}
Si sabes usar \texttt{pip}, sabes usar Pixi: \lstinline|pixi init|, \lstinline|pixi add|, \lstinline|pixi run|. Sin \texttt{apt}, sin \texttt{rosdep}, sin \texttt{source}, sin \texttt{sudo}.
\end{block}
\end{frame}

\midrule

\begin{frame}[fragile]{El \texttt{pixi.toml}}
%%CODE toml
[workspace]
# Para qué máquinas se resuelve (y se genera el lockfile)
platforms = ["linux-64", "osx-arm64", "win-64"]
# De dónde salen los paquetes: RoboStack para ROS, conda-forge para el resto
channels = ["robostack-lyrical", "conda-forge"]

[dependencies]
ros-lyrical-desktop = "*"

[tasks]
start = "ros2 launch my_package my_launch_file.launch.py"
%%END
\vfill
Vive en la \textbf{raíz} de tu workspace. Además: \lstinline|[activation]|, \lstinline|[environments]|, \lstinline|[target.<plataforma>]|, \lstinline|[pypi-dependencies]|\ldots
\end{frame}

\begin{frame}[fragile]{\texttt{pixi shell} y la activación}
\begin{columns}[T]
\column{0.45\linewidth}
\begin{terminal}
pixi shell
ros2 topic list
ros2 run turtlesim turtlesim_node
exit
\end{terminal}
\column{0.5\linewidth}
%%CODE toml
[activation]
scripts = ["install/setup.sh"]

[activation.env]
ROS_DOMAIN_ID = "42"
%%END
\end{columns}
\vfill
\begin{itemize}
    \item \lstinline|pixi shell| te mete en el entorno, como hacía \lstinline|source install/setup.bash|.
    \item \lstinline|pixi run| y \lstinline|pixi shell| activan el entorno primero, incluidos tus scripts.
    \item \lstinline|pixi shell-hook| imprime la activación como un script de shell normal (lo usaremos en Docker).
\end{itemize}
\end{frame}

\begin{frame}{El lockfile: el porqué de la reproducibilidad}
\begin{itemize}
    \item \lstinline|pixi.lock| fija versión exacta, build y \textbf{sha256} de cada paquete (conda y PyPI), \textbf{para cada plataforma declarada}.
    \item Se actualiza solo con \lstinline|pixi add| / \lstinline|pixi update|.
    \item \lstinline|pixi install --locked| $\rightarrow$ falla si el lockfile no está sincronizado (la CI).
    \item \lstinline|pixi lock --check| $\rightarrow$ la barrera barata en cada pull request.
\end{itemize}
\vfill
\begin{block}{Se commitea a git}
Todo el equipo, la CI y el robot instalan exactamente los mismos binarios. Es más fácil tirarlo que reconstruirlo cuando algo se actualizó sin que te enterases\ldots\ justo antes de la demo.
\end{block}
\end{frame}

\begin{frame}[fragile]{Compilar tu paquete con colcon}
Con ROS instalado y \lstinline|src/turtle_dancer/| en tu workspace:
\begin{terminal}
pixi add ros-dev-tools        # colcon, CMake y compiladores
pixi run colcon build
pixi workspace activation scripts add --target unix install/setup.sh
pixi run ros2 run turtle_dancer dance
\end{terminal}
\vfill
\begin{itemize}
    \item Igual que siempre, pero dentro del entorno: aparecen \lstinline|build/|, \lstinline|install/| y \lstinline|log/|.
    \item La activación carga el overlay por ti. Nada de \texttt{setuptools} ni \texttt{empy} fijados a mano.
\end{itemize}
\end{frame}

\begin{frame}[fragile]{Resolver para máquinas que no tienes}

pixi list --platform jetson        # lo que tendría la Jetson
\end{terminal}
\vfill
\centering Resolver es barato y portable; instalar es lo caro, y se hace donde toca.
\end{frame}

\begin{frame}[fragile]{Lo que escribes}
\begin{columns}[T]
\column{0.48\linewidth}
\small \texttt{pixi.toml} (workspace)
%%CODE toml
[workspace]
preview = ["pixi-build"]

[workspace.dependencies]
pixi-build-ros = ">=0.7.5"

[dependencies.ros-lyrical-turtle-dancer]
path = "src/turtle_dancer"
%%END
\column{0.48\linewidth}
\small \texttt{src/turtle\_dancer/pixi.toml} (paquete)
%%CODE toml
[package.build.backend]
name = "pixi-build-ros"
workspace = true
%%END
\end{columns}
\vfill
\begin{itemize}
    \item Nombre de la dependencia: el del \lstinline|package.xml| con el prefijo de la distro y guiones.
    \item \lstinline|CMakeLists.txt| y \lstinline|setup.py| no se tocan: el backend ejecuta tu build \texttt{ament}.
\end{itemize}
\end{frame}

\begin{frame}[fragile]{\texttt{pixi-build-ros} lee tu \texttt{package.xml}}
\begin{columns}[T]
\column{0.48\linewidth}
\small Lo que ya tienes
%%CODE xml tiny
<package format="3">
  <name>turtle_dancer</name>
  <version>0.1.0</version>
  <buildtool_depend>ament_cmake</buildtool_depend>
  <depend>rclcpp</depend>
  <depend>geometry_msgs</depend>
  <exec_depend>turtlesim</exec_depend>
  <export>
    <build_type>ament_cmake</build_type>
  </export>
</package>
%%END
\column{0.48\linewidth}
\small Lo que \textbf{no} tienes que escribir
%%CODE toml tiny
[package]
name = "ros-lyrical-turtle-dancer"
version = "0.1.0"
[package.build-dependencies]
ros-lyrical-ament-cmake = "*"
ros-lyrical-rclcpp = "*"
ros-lyrical-geometry-msgs = "*"
[package.run-dependencies]
ros-lyrical-rclcpp = "*"
ros-lyrical-geometry-msgs = "*"
ros-lyrical-turtlesim = "*"
%%END
\end{columns}
\vfill
\centering \small El \lstinline|package.xml| sigue siendo la única fuente de verdad. La distro la elige el canal del workspace.
\end{frame}

\begin{frame}{El bucle editar-ejecutar}
\begin{itemize}
    \item \lstinline|pixi install| construye el paquete en un entorno de build aislado y lo instala en tu entorno \textbf{como un paquete conda}, al lado de \texttt{turtlesim}.
    \item \lstinline|pixi run dance| comprueba antes las entradas (fuentes, \lstinline|package.xml|, \lstinline|CMakeLists.txt|, launch, mensajes\ldots) y reconstruye si algo cambió.
    \item Fuera: la task \texttt{build}, \lstinline|ros-dev-tools|, la activación, \lstinline|build/ install/ log/|.
\end{itemize}
\vfill
\begin{block}{}
\centering Editar $\rightarrow$ \lstinline|pixi run| $\rightarrow$ funciona. Desde una terminal nueva, sin \texttt{source} de nada.
\end{block}
\end{frame}

\begin{frame}{Backends de build}
Pixi no sabe compilar tu código. Un \textbf{backend} sí.
\vfill
\centering
\begin{tabular}{lll}
\toprule
\textbf{Backend} & \textbf{Construye} & \textbf{Lee} \\
\midrule
\texttt{pixi-build-ros} & Paquetes ROS & \lstinline|package.xml| \\
\texttt{pixi-build-cmake} & C y C++ & \lstinline|CMakeLists.txt| \\
\texttt{pixi-build-python} & Python & \lstinline|pyproject.toml| \\
\texttt{pixi-build-rust} & Rust & \lstinline|Cargo.toml| \\
\texttt{pixi-build-rattler-build} & Recetas conda & \lstinline|recipe.yaml| \\
\bottomrule
\end{tabular}
\vfill
\raggedright \small ¿Necesitas control total (parches, pasos de build propios)? Tu \lstinline|recipe.yaml| de \texttt{rattler-build} sigue valiendo: \lstinline|[package.build.config] recipe = "recipe.yaml"|.
\end{frame}

\seccion[Colaboración]{Colaboración, CI/CD y Docker}{De «funciona en mi máquina» a «funciona en la del equipo».}
%=================================================

\begin{frame}[fragile]{CI en dos líneas}
%%CODE yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: prefix-dev/setup-pixi@v0.10.2
        with:
          locked: true
      - run: pixi run test
%%END
\begin{itemize}
    \item Instala Pixi y el entorno desde el lockfile; ejecuta tu task.
    \item Las mismas tasks que en tu portátil: no hay un segundo setup en YAML que se desincronice.
    \item Caché gratis, con el hash de \lstinline|pixi.lock| como clave.
\end{itemize}
\end{frame}

\begin{frame}[fragile]{Docker: la etapa de build}
%%CODE docker
FROM ghcr.io/prefix-dev/pixi:0.80.0-noble AS build
WORKDIR /app
COPY pixi.toml pixi.lock ./
RUN pixi install --locked
RUN pixi shell-hook -s bash > /shell-hook.sh \
    && echo 'exec "$@"' >> /shell-hook.sh
%%END
\vfill
\begin{itemize}
    \item Parte de la imagen de Pixi y copia el manifiesto y el lockfile.
    \item \lstinline|--locked|: falla si el lockfile no cuadra; la imagen no puede contener algo que el equipo no probó.
    \item Escribe la activación en un script, para la siguiente etapa.
\end{itemize}
\end{frame}

\begin{frame}[fragile]{Docker: la etapa final}
%%CODE docker
FROM ubuntu:26.04 AS runtime
COPY --from=build /app/.pixi/envs/default /app/.pixi/envs/default
COPY --from=build /shell-hook.sh /shell-hook.sh
ENTRYPOINT ["/bin/bash", "/shell-hook.sh"]
CMD ["ros2", "run", "demo_nodes_cpp", "talker"]
%%END
\vfill
\begin{itemize}
    \item Una imagen base normal, sin el binario de \texttt{pixi}.
    \item Recibe el entorno terminado y el script de activación.
    \item Portátil, CI e imagen instalan desde el mismo \lstinline|pixi.lock|.
\end{itemize}
\end{frame}

\begin{frame}[fragile]{\texttt{pixi-pack}: un entorno en un fichero}
\begin{columns}[T]
\column{0.45\linewidth}
\small En tu portátil
\begin{terminal}
pixi-pack \
  --platform linux-aarch64 \
  pixi.toml
\end{terminal}
\column{0.5\linewidth}
\small En el robot
\begin{terminal}
pixi-unpack environment.tar
source activate.sh
ros2 run demo_nodes_cpp talker
\end{terminal}
\end{columns}
\vfill
\begin{itemize}
    \item Para despliegues sin red, con 4G poco fiable o sin Docker.
    \item En el destino no hace falta Pixi, ni conda, ni conexión.
    \item \lstinline|--create-executable|: un único fichero autoextraíble.
\end{itemize}
\end{frame}

%=================================================
\seccion[Workspace real]{Compilar un workspace real}{Repositorios de otros, sin \texttt{rosdep}, y un Kobuki en una casa.}
%=================================================

\begin{frame}{La vida real: un \texttt{src/} con repositorios de otros}
\begin{itemize}
    \item Lo de siempre: clonar, \lstinline|rosdep install|, \lstinline|colcon build|, \lstinline|source|.
    \item \texttt{rosdep} no sirve dentro de Pixi: llama a \texttt{apt} y \texttt{pip} del sistema, con \texttt{sudo} y sin fijar versiones.
    \item Lo que hace \texttt{rosdep} es traducir cada dependencia del \lstinline|package.xml| a un paquete. Con RoboStack la traducción es directa:
\end{itemize}
\vfill
\centering
\scriptsize
\begin{tabular}{lll}
\toprule
\textbf{En el \texttt{package.xml}} & \textbf{Con \texttt{rosdep}} & \textbf{Con Pixi} \\
\midrule
\texttt{ros\_gz\_sim} & \texttt{apt install ros-lyrical-ros-gz-sim} & \texttt{pixi add ros-lyrical-ros-gz-sim} \\
\texttt{xacro} & \texttt{apt install ros-lyrical-xacro} & \texttt{pixi add ros-lyrical-xacro} \\
\bottomrule
\end{tabular}
\vfill
\raggedright\small Y queda escrito en el \lstinline|pixi.toml| y fijado en el \lstinline|pixi.lock|. Para workspaces grandes, \texttt{pixi-ros} hace la traducción por ti.
\end{frame}

\begin{frame}[fragile]{Los repositorios, en un fichero: \texttt{workspace.repos}}
%%CODE yaml
repositories:
  easynav_playgrounds:
    type: git
    url: https://github.com/EasyNavigation/easynav_playgrounds.git
    version: pichi-workshop      # solo el Kobuki y la casa
  teleop_twist_keyboard:
    type: git
    url: https://github.com/ros2/teleop_twist_keyboard.git
    version: rolling
%%END
\begin{terminal}
vcs import --input workspace.repos src     # vcstool viene en ros-dev-tools
\end{terminal}
\vfill
\small El formato estándar de ROS para describir un workspace: va a git junto al \lstinline|pixi.toml| y el \lstinline|pixi.lock|.
\end{frame}

\begin{frame}[fragile]{El entorno y las tasks: \texttt{pixi.toml}}
\begin{columns}[T]
\column{0.4\linewidth}
%%CODE toml
[dependencies]
ros-lyrical-ros-base = ">=0.13"
ros-dev-tools = ">=1.0"
ros-lyrical-ros-gz-sim = "*"
ros-lyrical-ros-gz-bridge = "*"
ros-lyrical-gz-sim-vendor = "*"
ros-lyrical-xacro = "*"
# ...

[target.unix.activation]
scripts = ["install/setup.sh"]
%%END
\column{0.57\linewidth}
%%CODE toml
[tasks.importar]
cmd = "mkdir -p src && vcs import --input workspace.repos src"

[tasks.build]
cmd = "colcon build"
depends-on = ["importar"]

[tasks.sim]
cmd = "ros2 launch easynav_playground_kobuki_worlds gazebo_sim.launch.yaml"
depends-on = ["build"]
%%END
\end{columns}
\vfill
\centering \lstinline|git clone| · \lstinline|cd| · \lstinline|pixi run sim|: clona, compila y lanza Gazebo con el Kobuki.
\end{frame}
